# Architecture Notes

Reference for patterns that come up when extending the app. Consult when adding new engines, top-level pages, or cross-tab features.

## Lazy WASM loading

Each non-default engine is loaded on first use via a cached promise:

- **manifold-3d** — eager on app boot (needed for `Manifold.ofMesh`, paint persistence, slicing).
- **OpenSCAD** — `await import('openscad-wasm-prebuilt')` in `openscadEngine.init()`. Triggered on first SCAD session open or first SCAD run.
- **OpenCASCADE / replicad** — `await import('replicad')` + WASM in `ensureBrepLoaded()` (`brepRuntime.ts`). Triggered by (a) `api.BREP.*` use in a manifold-js session, or (b) first replicad-language session run.
- **WebLLM** — `await import('@mlc-ai/web-llm')` in `src/ai/local.ts`. Triggered on first local-model use.

Each loader is idempotent and caches the resolved module. Vite splits each into its own chunk (verify via `npm run build` output — the OCCT WASM lands as `replicad_single-*.wasm` (~10 MB) outside the main bundle).

When adding a new lazy-loaded module, follow `brepRuntime.ts`'s pattern: one `ensureXLoaded()` promise, cached after success and cleared on failure so the next call retries.

**Loaders that run in the engine Worker must not use the global `fetch`** — it does not exist there after the sandbox lockdown (next section). Use `fetchAppAsset(url)` from `src/geometry/workerLockdown.ts` for every runtime asset (WASM side-car, library sources, fonts), and hand Emscripten modules the bytes yourself (`wasmBinary`, as `brepRuntime.ts` does for OCCT) or use an inline-WASM build (OpenSCAD) so their glue never reaches for `fetch`/`XMLHttpRequest`. Dynamic `import()` of JS chunks keeps working.

**And their glue must survive frozen intrinsics.** SES `lockdown()` runs before any engine initialises (see [SES compartment for model code](#ses-compartment-for-model-code-1127)), so an Emscripten/embind module that assigns an inherited built-in property (`X.prototype.constructor = …`, `this.message = …` in an Error subclass) throws the "override mistake" when it initialises. Add the package to `isSesGlueModule` in `src/geometry/sesGlueFix.ts` and pin its rewrite count in `tests/unit/sesGlueFix.test.ts`.

## Engine Worker sandbox lockdown (#1090)

Model code runs — since #1127 inside an SES Compartment (see the next section), or via `new Function('api', code)` with the SES kill switch on — in the geometry Worker (`src/geometry/engineWorker.ts`, also spawned N× by `enginePool.ts` for Assembly / multi-part export). The Worker shares the page's origin, so unrestricted model code could read IndexedDB (AI provider keys live there) and exfiltrate over `fetch` (CSP `connect-src` allows `https:`). Untrusted code reaches the Worker through forked share links and imported `.partwright.json` files.

How it's locked down (`src/geometry/workerLockdown.ts`):

- **When.** `engineWorker.ts` calls `lockdownGlobalScope(self)` right after the `init` handshake (manifold-3d's WASM is fetched during init, before any model code exists) and before posting `ready`. Every other message type first awaits `ensureSandboxLocked()`, so even a protocol violation (an `execute` before `init`) can't run model code on an unlocked scope. It is **fail-closed**: if `verifyLockdown` finds anything still reachable, the Worker refuses to run model code.
- **What.** Each name in `LOCKDOWN_GLOBALS` (fetch, XHR, WebSocket(Stream), EventSource, WebTransport, RTC, indexedDB + `IDB*`, caches/CacheStorage, cookieStore, Storage/Lock managers, file-system entry points, Worker/SharedWorker, BroadcastChannel, ServiceWorker containers, ShadowRealm, FontFace/fonts, Notification) is deleted from the global object **and every object on its prototype chain** (Chromium puts `fetch`/`indexedDB` on `WorkerGlobalScope.prototype`), then pinned on the global as a non-writable, non-configurable `undefined` so it can't be re-added. `NAVIGATOR_PROPS` (storage, storageBuckets, locks, serviceWorker, sendBeacon, usb/hid/serial/bluetooth) get the same treatment on `navigator`. `importScripts` and `close` become frozen throwing stubs — `importScripts` deliberately stays a *function* because the OCCT Emscripten glue detects "Worker" via `typeof importScripts == 'function'` (OpenSCAD's checks `WorkerGlobalScope`, which is kept). `onmessage`/`postMessage` are pinned as non-writable own properties so model code can't swap the Worker's handler. `URL` itself stays (asset paths are resolved with it), but its statics `URL.createObjectURL`/`URL.revokeObjectURL` (`URL_STATIC_STUBS`) become frozen throwing stubs: a `blob:` URL lands in the origin-wide blob registry, a write channel any same-origin context can read. Nothing in the engine Worker graph calls them; `verifyLockdown` checks they are still our pinned stubs.
- **Allowlist audit (default deny).** The denylist above only covers capabilities someone thought of; the next browser release can add a new storage or transport API to the Worker global. So, last step of `lockdownGlobalScope`, every own property — string **and** symbol keys — of the global and of each object up its prototype chain (`DedicatedWorkerGlobalScope.prototype` → `WorkerGlobalScope.prototype` → `EventTarget.prototype` → `Object.prototype`), and of `navigator` and its chain (`WorkerNavigator.prototype` → `Object.prototype`), is checked against the grouped, commented allowlist in `src/geometry/workerGlobalAllowlist.ts` (string keys against each group's `names`, symbol keys — labelled `@@toStringTag`, `@@for(key)`, `@@unique(description)` — against its `symbols`, so the two namespaces can't match each other) (`GLOBAL_ALLOWLIST` / `NAVIGATOR_ALLOWLIST`: ECMAScript built-ins, `WebAssembly`, scope identity + EventTarget plumbing, read-only scope info like `location`, the pinned message channel, error handlers, the lockdown stubs, timers, in-memory data utilities (TextEncoder/Decoder, atob/btoa, structuredClone, Blob, URL, DOMException, Event), `performance`, `crypto` (incl. `subtle`, pure computation), `console`; on navigator only static environment facts like `hardwareConcurrency`/`userAgent`). A name that is not listed and not **inert** — a data property holding a primitive, which covers the names already pinned to `undefined`, WebIDL constants such as `TEMPORARY`/`PERSISTENT` (non-configurable, so undeletable) and library counters like style-mod's `Symbol.for("ͼ")` — is deleted from every chain object and pinned to `undefined` exactly like a denylisted one. `verifyLockdown` re-runs the audit, so anything that can't be removed fails the lockdown closed. The removals come back as `LockdownReport.defaultDenied`, which `engineWorker.ts` logs with `console.debug('[lockdown] default-deny removed N non-allowlisted globals: …')` — in today's Chromium ~229 names in the direct Worker (WebGPU/WebGL/WebCodecs interfaces, `OffscreenCanvas`, `createImageBitmap`, `MessageChannel`, `Request`/`Response`, Streams, `navigator.gpu`/`permissions`/`connection`/`userAgentData`, …) and ~145 in the #1110 iframe-sandbox Worker (a classic blob: Worker, so its bootstrap's `var q`/`function h` globals are swept too). The audit is the last step, after every capability an engine needs privately has been captured (only `fetch`, via `fetchAppAsset`); the lazy engines that load after lockdown (OpenSCAD + BOSL2 + fonts, OCCT for `api.BREP` and replicad sessions + STEP import/export, opentype for `api.text`, the SDF/deform/simplify paths, the Assembly pool) were traced and touch no non-allowlisted global apart from opentype's module-load `typeof DecompressionStream` probe, which falls back to its built-in inflater. The allowlist module is pure (no imports) so the unit tier tests the planner (`tests/unit/workerGlobalAllowlist.test.ts`) and the e2e test re-runs it on names enumerated inside the real Worker, direct and iframe-sandboxed (`tests/engine-lockdown.spec.ts` → "the Worker global holds only allowlisted names"). The in-Worker enumeration is JS source (`tests/helpers/enumerateChainSource.ts`); a unit test evaluates that same text against a fake global and compares it with the runtime `enumerateChain`, so the two can't drift.
  - **What the guarantee rests on.** The audit removes capability *entry points* — the globals and navigator members through which a capability is obtained — not every way to name an interface. A removed constructor is still reachable from an instance of it (`new Blob([]).stream().constructor` is `ReadableStream`, `navigator.constructor` is `WorkerNavigator`, a received event's `constructor` is `MessageEvent`); that's fine because such constructors carry no capability of their own. Never allowlist (or leave reachable) an object that *hands out* a capability — the way `navigator.storage` or `fetch` does — on the theory that its interface object was removed.
  - **When it fails closed.** If a browser exposes a global that is neither allowlisted nor removable (a non-configurable accessor or object binding), the Worker refuses to run **any** model code. The Worker sends `formatLockdownRefusal(…)` (`src/geometry/lockdownRefusal.ts`) — "Geometry engine refused to start for security reasons: … (still reachable: <names>)" — which is the error every run then shows, and the main thread (`engine.ts` for the editor Worker, `enginePool.ts` for the Assembly/export pool, via `reportLockdownRefusal` in `lockdownRefusalLog.ts`) records it once per page in the Diagnostic Log as an `error` with `source: 'engine'`, naming the globals (the pool stops instead of respawning into the same refusal). CI only runs Chromium, so this is most likely to show up in Firefox, WebKit or a newer Chrome than CI's. The fix is an allowlist entry for the named global, after checking it grants no network, storage or cross-context capability (next bullet).
  - **Adding an allowlist entry.** You need one when an engine or a library starts reading a global the audit removes, when a user's Diagnostic Log shows "engine refused to start for security reasons" naming an unremovable global (non-Chromium browsers especially) (an engine e2e spec breaks; run the failing flow and look for the name in the `[lockdown] default-deny removed …` debug line in the Worker console), or when a Chromium upgrade adds a capability that can't be deleted (the e2e test fails and names it). Add the name to the group in `workerGlobalAllowlist.ts` it belongs to, or a new group with a one-line `why`, **only if it grants no network, storage or cross-context capability** (it's inert data, pure computation, or this-Worker-only scheduling). Never allowlist a denylisted name: a pinned `undefined` is already accepted, and listing it would also accept the live capability (a unit test enforces this). If an engine needs something model code must not have, capture it privately in `workerLockdown.ts` before the removal, the way `fetchAppAsset` captures `fetch`, and expose only a narrow wrapper.
- **Private fetch.** Just before removing `fetch`, the lockdown captures it **pre-bound** into module scope (never on `self` or `api`). `fetchAppAsset(url)` is the only door to it: a same-origin GET with `redirect: 'error'` and a null-prototype init (a polluted `Object.prototype` can't add method/body/headers), for a path under the frozen prefix allow-list (`<base>assets/`, `<base>openscad-libs/`, plus `<base>node_modules/` on the dev server) with no `.`/`..`/empty segments, query or fragment. The check (`toAppAssetPath`) uses only operations model code can't monkey-patch (typeof, primitive string indexing, comparisons, loops over frozen arrays), and the loaders (`textGlyphs`, `fontsLoader`, `bosl2Loader`) build their URL lists at module load, iterate with plain loops and vet manifest names with `isSafeAssetName`, so patched built-ins can't steer them either. Even a model that reaches the function via `import()` of the bundled chunk can only cause a same-origin GET of a public static asset. Outside a locked realm (main thread, Node SSR for `model:preview`, unit tests) `fetchAppAsset` defers to the live `globalThis.fetch`, so the CLI's `public/` fetch shim still works.
- **Not removable: dynamic `import()`.** It's syntax, not a global. CSP `script-src` (`'self'` + the fixed Cloudflare analytics host; no `blob:`/`data:`) bounds it to same-origin modules, and the CSP is delivered with the Worker script response, so it applies inside the Worker.
- **Main thread treats Worker messages as untrusted data.** `engine.ts` and `enginePool.ts` run every Worker→main message through `checkEngineWorkerMessage` (`src/geometry/workerMessageValidation.ts`): type allow-list; meshes with typed-array classes, lengths and triangle-index ranges checked, and **every typed array required to own a plain, non-resizable `ArrayBuffer`** (a `SharedArrayBuffer`-backed view — postable because the app is cross-origin isolated — could be rewritten after the check); plain-data payloads with no `__proto__`/`constructor` keys, bounded depth and a total node budget with shared references visited once (so a `x=[x,x]`×31 DAG can't stall the main thread); `api.paint.*` descriptors allow-listed by kind from the shared `API_PAINT_DESCRIPTOR_KINDS` (`src/geometry/apiPaintSpec.ts`, which the recorder's types also use) with per-kind field checks; `surfaceOps` re-run through `parseSurfaceOpts`, `paramsSchema` through `normalizeParamSchema`, and `materialSpec` checked against the presets and 0..1 ranges. A malformed message fails the matching request with a clear error and **recycles** the Worker (its realm is no longer trustworthy); a malformed progressive preview is just dropped. `VoxelGrid.fromTransfer` re-validates voxel grids the same way.

- **No main-thread evaluation.** Every engine entry point that runs model code (`manifoldJsEngine.run`, `voxelEngine.run`, `runVoxelGrid`, `runReplicadAsync`) calls `assertModelCodeRealm()` and throws in a document realm; there is no synchronous main-thread `executeCode`. `validateCode` stays compile-only (`new Function` is built, never called). Voxel export (VOX / greedy STL) and the synchronous `activateVoxelPaint()` use the grid the Worker returned with the last render (`MeshResult.voxelGrid` → `lastVoxelRun` in `main.ts`, keyed on the code + the Customizer values the run was requested with, and also kept in the per-version `partMeshCache` so switching back to an object restores it → `VoxelGrid.fromTransfer`, which re-validates every key/colour/surfacing knob); the Voxel Studio button and the async VOX exports fall back to the Worker's `voxel_grid` message when the cache is stale. `setReferenceGeometry` and `exportParamSweep` use `executeCodeAsync`. Node CLIs (`model:preview`, segmentation) have no `document` and still run engines directly on the user's own local files.
- **Cross-session isolation.** The Worker realm persists across runs, so model code could patch built-ins or add a `message` listener to watch (or forge results for) later runs. `src/geometry/trustDomain.ts` holds the active trust domain — the open session (`sessionTrustDomain(sessionId)` in `main.ts`, set from an `onStateChange` listener registered at the top of `main()` so even boot-time runs are tagged; before that the `(startup)` sentinel applies). Every engine request calls `claimEngineWorker()`, which recycles a Worker tagged with a different domain (a quiet `'debug'` recycle: no health-panel restart, no Diagnostic Log entry), tags the Worker with the request's domain, and after `await workerReady` re-checks (`ensureClaim`) that the same Worker and domain are still current before posting. Flows that capture code and then await (thumbnail backfill, `exportParamSweep` frames, compose/merge bakes, multi-object export bakes, the Assembly view) pass the domain they captured; once the session has changed they are refused instead of running in the next session's Worker. The parallel `enginePool` disposes itself on every domain change and refuses builds for a stale domain, so an old flow can't respawn it. Within one session the realm is shared — including with objects merged in from a file, which join the session's domain (no recycle on merge, so a STEP-as-BREP object's Worker-held imports survive). That's the trust boundary. Measured cost: the first run after a session switch pays a fresh Worker + manifold-3d init (~0.2–0.3 s in the e2e run vs ~15 ms warm). Since #1127 model code can't reach the realm (SES, next section) and the JavaScript objects runs share are hardened, but the manifold-3d WASM heap is still shared within a session (embind instances' `$$` records let model code read/write it — see docs/engine-sandbox.md → "SES compartment"), so the per-session Worker stays the boundary for engine state (WASM heaps, BREP imports) and defence in depth.

Tests: `tests/unit/workerLockdown.test.ts`, `tests/unit/workerGlobalAllowlist.test.ts`, `tests/unit/workerMessageValidation.test.ts`, e2e `tests/engine-lockdown.spec.ts` (hostile probes in manifold-js + voxel with the SES kill switch on, forged messages, SCAD + BOSL2 + fonts, BREP lazy load + STEP export after lockdown, the global-allowlist audit in the direct and iframe-sandbox Worker).

## SES compartment for model code (#1127)

The realm lockdown above strips capabilities from the Worker global, but model code still *shared the realm* with the engines: it could patch `Array.prototype`, `JSON`, `Function.prototype.call` or `api.Manifold.prototype` and so steer engine code and later runs, reach the Worker global through `Function('return this')()`, or listen on its message channel. So model code now runs in a [Hardened JavaScript](https://github.com/endojs/endo/tree/master/packages/ses) (SES) `Compartment`, **on by default**:

- **Ordering — the rule.** In `engineWorker.ts`'s `init` handler: **(1) SES `lockdown()`** (`enableSesSandbox` in `src/geometry/sesSandbox.ts`), **(2) engine init** (manifold-3d; OpenSCAD and OpenCASCADE load lazily later, on already-frozen intrinsics), **(3) `workerLockdown`'s denylist + default-deny global audit** (previous section). No engine may initialise against unfrozen intrinsics, and the audit runs last so it sees the globals SES installed. A request that races ahead of `init` (`ensureSandboxLocked`) still runs SES first. The `init` message carries `ses: boolean`; anything but an explicit `false` means on.
- **Lockdown preset** (`SES_LOCKDOWN_OPTIONS` in `src/geometry/sesModelSource.ts`). Two options are load-bearing, and both were measured: `evalTaming: 'unsafe-eval'` (the default `'safe-eval'` routes the *engine's own* `new Function` code — `sdfCompile.ts` SDF trees, embind invokers — through SES's `with`-scope evaluator, making SDF figures 4.3× slower; compartments never get the native evaluators either way) and `overrideTaming: 'min'` (`'moderate'`/`'severe'` turn shared-prototype data properties such as `%TypedArray%.prototype.*` and `Array.prototype.push` into accessors, which knocks V8 off its fast paths: BOSL2 SCAD ~2× slower). `errorTaming: 'unsafe'`, `stackFiltering: 'verbose'`, `consoleTaming: 'unsafe'`, `localeTaming: 'unsafe'` and `errorTrapping`/`unhandledRejectionTrapping: 'none'` keep the engine realm's errors, stacks, console, locale behaviour and the Worker's own unhandled-rejection relay exactly as before.
- **Glue fix** (`src/geometry/sesGlueFix.ts`). With `overrideTaming: 'min'`, the Emscripten/embind glue of manifold-3d and replicad-opencascadejs hits the override mistake (`errorClass.prototype.constructor = …`, `.toString = …`, `this.message = …`, `this.constructor = …`, `FS.ErrnoError.prototype.constructor = …`). A Vite `transform` plugin (`sesOverrideMistakeFix` in `vite.config.ts`, registered for the main and the Worker bundles) rewrites exactly those assignments into an own-property define with the same result. Semantics are identical with SES off. `tests/unit/sesGlueFix.test.ts` runs the rewrite over the **installed** glue files and pins the count per file (manifold.js 5, replicad_single.js 7), so a dependency bump that changes the glue fails CI instead of breaking BREP at runtime. OpenSCAD needs no rewrite.
- **A compartment per run.** `compileModelCode()` (`src/geometry/modelEval.ts`, the single choke point that the seven former `new Function` sites in the manifold-js / voxel / replicad engines use) builds a fresh `Compartment` for every compile, so nothing a run puts on its `globalThis` survives. The source is wrapped (`wrapModelSource`) so the compartment's globals are bound as local `const`s first. Without that "prelude", every free-variable read goes through SES's `with` chain and hot model closures (a `levelSet` SDF callback) run 1.85× slower. The wrapper head shares the user's first line, so user line N is line N of the evaluated source.
- **What model code can name.** The compartment's own globals (the ECMAScript built-ins SES permits, including `TextEncoder`/`TextDecoder`), plus hardened endowments (`buildEndowments`): the start compartment's `Math` (with `random`) and `Date` (with `now()`), `Float16Array`/`Float32Array`/`Float64Array` (SES omits them), a `console` of forwarding functions, and `performance` with only `now()`. Deliberately absent: the Worker global (`self`, `postMessage`, `onmessage`, `importScripts`, `location`, `navigator`), timers and `queueMicrotask` (their callbacks would outlive the run), `fetch` and storage, `WebAssembly`, `SharedArrayBuffer`/`Atomics`, `crypto`, `URL`, `Blob`, `structuredClone`, `Intl`, `WeakRef`/`FinalizationRegistry`. No catalog entry or example uses any of them; between them they use `Math`, `Map`, `Set`, `Array`, `String`, `Number`, `Object`, `Error`, `Float32Array`, `parseInt` and `Infinity`.
- **No shared mutable state between runs.** Lockdown freezes the intrinsics, but objects the *engines* create and hand to model code live across runs in the same Worker. So each engine calls `hardenModelShared(api)` before running the code. That deep-freezes everything reachable from that run's `api` — the embind classes, the namespace singletons, BREP, imports — and is the identity function without SES. Engines also harden the shared classes their return values come from (`SdfNode`, `VoxelGrid`). Rules for new code that model code can reach:
  - The manifold-3d run wrappers (allocation tracking and primitive guards in `manifoldJs.ts`) are **installed once** and read the active run's tracker from a module variable, instead of patching and restoring the classes around every run. That's what lets `Manifold`/`CrossSection` and their prototypes be hardened. `ensureManifoldRunWrappers()` must run before anything hardens them (the replicad engine exposes `Manifold` too). `hardenInstanceReachables` hardens what instances reach but `api` doesn't: manifold-3d's JS `Mesh` class and embind's per-class `$$.ptrType` descriptors.
  - **Never hand model code an engine-internal object whose graph outlives the run and can't be frozen.** A replicad shape reaches the whole OpenCASCADE Emscripten module (`shape.oc`: every embind class, the WASM heap views, `_malloc`, `FS`, `dynCall_*`), which Emscripten itself mutates. So `BrepShape` wrappers keep the replicad shape and the label data in a module-private `WeakMap` (`BREP_INTERNALS` in `brepRuntime.ts`; `isBrepShape()` replaces the old `'_shape' in x` checks), and the wrapper itself is just methods.
  - Error classes defined in Worker modules (`class ValidationError extends Error`) were evaluated **before** lockdown, so their `[[Prototype]]` is the *original* `Error`. Lockdown replaces that on `globalThis` but leaves it unfrozen, and it holds V8's live `prepareStackTrace` hook: model code that set it would intercept every stack in the realm, later runs included (verified before the fix). `enableSesSandbox` hardens the original `Error`, `Date` and `RegExp` after lockdown, and fails closed if they aren't frozen. It also hardens `ValidationError` and `Blob` (BREP `blobSTEP()`); `hardenInstanceReachables` hardens the glue's own error classes (`ManifoldError`, embind's `BindingError`/`InternalError`/`UnboundTypeError`, plus whatever a bad-argument call, an invalid mesh and a use-after-delete actually throw), and `brepRuntime.ts` does the same for OpenCASCADE's embind error classes after OCCT init. A new class whose instances reach model code needs the same. `tests/engine-ses.spec.ts` "no shared mutable state" stamps every writable object reachable from `api`, and from what common api calls return (thrown errors included), in one run, and fails if the next run finds a stamp.
- **Error UX** (`sesModelSource.ts`).
  - **Undeclared names throw `ReferenceError`, as in strict JS.** SES's scope terminator reads an unknown name as `undefined`, so a typo (`Manfold.cube()`, `return zzznotdefined123`) would fail later with a misleading message, and `const s = siz || 10` would silently change meaning. SES has no option to make unknown names throw, so `analyzeFreeGlobals` finds the names nothing in the source declares (any declaration of the name, in any scope, excludes it — deliberately conservative) and the compiler installs a throwing accessor for each on that run's compartment global. A local binding always shadows the accessor, so `ReferenceError: <name> is not defined` fires exactly when, and only if, such a read executes: dead code, uncalled helpers and `typeof x` guards (`rewriteFreeTypeof` turns the operand into a call to a per-compartment helper that answers `'undefined'` while `x` is still the trap and the real type once the code has made `x` a global) are unaffected, and a scope-analysis mistake can't produce a false error. Assigning a trapped name throws the same `ReferenceError` (strict JS: `widht = 20`, `for (i = 0; …)` with no declaration). Names the code itself puts on `globalThis` (`globalThis.x = …`) are never trapped, and when the code can create globals the analysis can't name — `globalThis[k] = …` with a computed key, `globalThis` used as a value (`Object.assign(globalThis, …)`, `const g = globalThis`), or any `eval` — `analyzeFreeGlobals` sets `globalThisEscapes` and assigning a trapped name instead creates the global, since it can't be told apart from `globalThis[k] = v`. Names the compartment global inherits (`toString`, `hasOwnProperty`, …) are never free. The analysis bails out entirely (nothing trapped) on any Lezer error node — a syntax error, syntax newer than the grammar, or a unicode-escaped identifier (`let \u0061`), which Lezer can't decode. It parses the whole source on each run (~0.5 ms per KB: ~8 ms for `cat_calico`, ~176 ms for the 363 KB `benchy-reconstruction`), so sources longer than AppConfig `geometry.sesUndeclaredCheckMaxChars` (default 150 000, passed to each engine Worker in its `init` message) skip it, and the last four results are cached (validate + run parse once). Sharing the parse with `neutralizeSesRejections` would only help sources that contain `import(`/`eval(`/HTML markers, the only ones that parse twice, so it isn't done. The error carries `modelLineNumber` — the line of the read, from the V8 stack (Chromium; Firefox/Safari fall back to the first reference) — which `modelCodeDiagnostics` (sourceDiagnostics.ts) turns into a located editor diagnostic. Known gap: a name declared *somewhere* but read outside its scope still reads as `undefined`.
  - SES refuses source containing `import(`, `eval(`, `<!--` or `-->` **anywhere**. `neutralizeSesRejections` rewrites those inside comments (a length-preserving mangle) and in string/template literal text (`\x28`-style escapes: the value is unchanged, and the escape is a syntax error outside a literal, so a misparse can't turn it into code). It also spaces a mid-line `-->` in code (`i --> 0`). Real `import(…)`/`eval(…)` calls, `<!--` in code and a line-leading `-->` are still refused. `explainSesRejection` turns SES's `<unknown>:N` into "rejected on line N" plus a hint, and sets `modelLineNumber` so `javaScriptSyntaxDiagnostics` squiggles that line.
  - SES's own `__evadeHtmlCommentTest__` / `__evadeImportExpressionTest__` evaluate options were tried and not used: they rewrite string literal contents too, and turn a real `import(` into a call to an undefined `__import__`, which fails later with a confusing runtime error.
- **Fail closed.** If loading SES, `lockdown()`, the frozen-intrinsics checks or the compartment self-test (`typeof postMessage` etc. must be `'undefined'`) throws, `lockdownNow()` refuses model code with `formatLockdownRefusal('SES lockdown failed: …')`. That's the same "Geometry engine refused to start for security reasons" message and Diagnostic Log entry as a failed global audit (`lockdownRefusalLog.ts`, for the editor Worker and the Assembly pool). The dev-only flag value `partwright.sesSandbox = 'test-fail'` simulates it end to end (e2e "an SES lockdown failure fails closed").
- **Allowlist entries.** SES installs `lockdown`, `repairIntrinsics`, `hardenIntrinsics` (only once `repairIntrinsics` runs), `harden`, `Compartment`, `assert` and the registry symbol `@@for(MAKE_CAUSAL_CONSOLE_FROM_LOGGER_KEY_FOR_SES_AVA)` on the Worker global. They are capability-free and listed in the `ses` group of `workerGlobalAllowlist.ts`. Model code can't see the Worker global, so the e2e audit test inspects it from the engine side: the dev-only `inspect_realm` message (`inspectEngineRealm()` in `engine.ts`) returns `enumerateChain` for the global and navigator, the URL statics, the compiler name, and whether the intrinsics are frozen.
- **Kill switch.** `localStorage['partwright.sesSandbox'] = 'off'` (per browser profile) or `VITE_SES_SANDBOX=0` (the build/dev default; localStorage wins) — `src/geometry/sesSandboxFlag.ts`. Off is exactly the pre-#1127 behaviour: `ses` is never loaded and model code is compiled with `new Function`. It's for diagnosing an SES regression, not a user setting, and there is deliberately no AI tool for it.
- **Not covered.**
  - The Node `model:preview` / segmentation CLIs run `compileModelCode` **without** SES: they run the user's own local files, and locking down the Node/Vite realm would also freeze the SSR runtime's intrinsics. So a model that uses `setTimeout`/`navigator` previews fine headless but fails in the browser; check anything beyond plain JS in the browser.
  - The WASM heap: SES doesn't cover WebAssembly memory, and embind's per-instance `$$` records (writable, mutated by embind itself, so not hardenable) let model code read, write and free manifold-3d heap memory that persists across runs in a session.
  - CPU and memory exhaustion are unchanged.
  - The returned data is still untrusted, so #1109's message validation stays essential.

## Browser history — back button preservation

`updateURL()` in `sessionManager.ts` uses `history.replaceState`, not push — intentional for in-editor updates (version switching, rename) that shouldn't pollute the back stack. But it's a trap for cross-page navigation:

- If any session-mutating function (`openSession`, `createSession`, `closeSession`, `importSessionPayload`) runs **before** you push the destination history entry, the internal `replaceState` overwrites the origin page and breaks the back button.
- **Always push the destination entry first**, then run the state change. See `handleCatalogEntryLoad` and `openSessionFromLanding` in `src/main.ts` for the canonical ordering.
- For in-page "Back" buttons on top-level pages (catalog, help), prefer `window.history.back()` when there's a real prior entry — falling back to `replace` (not push) when the page was loaded directly by URL. See `helpHasAppBackTarget` / `catalogHasAppBackTarget`.

When adding a new top-level page or cross-page navigation, walk through:
1. What's on the back stack before this navigation fires?
2. What does `window.location` look like after each async step (especially DB or session ops)?
3. Does back take the user to the prior page, not two pages back?

## Cross-tab isolation — implementation patterns

The rule: state must not bleed between tabs. The explicit exceptions are opening a session in a tab and taking control of a session in another tab.

Concretely:

- **Don't put session-scoped state in a shared localStorage blob.** AI provider/model/toggles are per-tab working state, persisted per-session on `session.aiPreference` and applied only on open/take-control — see `applySessionAiPreference`/`recordSessionAiPreference` in `aiPanel.ts` and `setSessionAiPreference` in `sessionManager.ts`. `reloadSettingsFromStorage` deliberately preserves this tab's `toggles`/`preset` when a peer tab writes the shared blob — it adopts only genuinely-global additive prefs (custom models, system-prompt overrides, panel width).
- **App-level preferences** (units, render quality, editor auto-format) use `readPerTabPref`/`writePerTabPref` (`src/storage/perTabPref.ts`): live value in sessionStorage (per-tab) with a localStorage seed so a fresh tab still inherits the last choice. Don't attach a `storage` listener that live-mirrors them.
- **`storage`-event and `BroadcastChannel` handlers** must gate on `msg.sessionId === currentState.session?.id` before acting — see `tabSync.ts` consumers and `sessionLock.ts`. Never adopt a peer's provider/model/toggles live.
- **Truly-global state** (custom local models, system-prompt overrides) is the exception and must be additive/merge-friendly so a peer tab's write can't clobber another tab's addition.
