## Lacked
- `git fetch origin main claude/ecstatic-ritchie-1d6z8t` (multiple refs in
  one call) failed outright with `fatal: couldn't find remote ref
  claude/ecstatic-ritchie-1d6z8t` even though `origin main` alone would have
  succeeded — one bad ref aborts the whole fetch instead of fetching what it
  can. Cost one extra round-trip splitting the fetch into two separate calls
  to isolate which ref was the problem.
- `git push` printed `This repository moved. Please use the new location:
  https://github.com/kemper/partwright.git`, and the created PR's URL came
  back under `kemper/partwright` even though the GitHub MCP calls were made
  with `owner: kemper, repo: mainifold` (the session's actual scoped repo)
  and succeeded. Nothing broke this time, but a future session that reads
  its *own* PR URL back and treats `partwright` as the addressable repo name
  for subsequent MCP calls would get repo-scope errors — worth a heads-up
  that the identifiers can diverge (push remote vs. MCP `repo` param vs.
  the URL GitHub hands back).

## Learned
- The local branch `claude/ecstatic-ritchie-1d6z8t` had a stale
  remote-tracking ref (`remotes/origin/claude/...`) pointing at `main`'s tip
  from container setup, even though the branch had never actually been
  pushed — `git branch -a` alone can't distinguish "already pushed, in
  sync" from "local scaffolding ref, never pushed." `git fetch origin
  <branch>` failing with "couldn't find remote ref" is the reliable signal;
  don't trust `git log --oneline origin/<branch>` without fetching first.
