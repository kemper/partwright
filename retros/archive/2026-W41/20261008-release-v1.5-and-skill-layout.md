## Liked / Worked
- The gate pipeline itself was solid. main → staging was green all along, and
  `release-tag.yml` tagged and published v1.5.0 with grouped notes on its own.
- `/whats-new` on the live site is a clean proof that a deploy landed, because
  the new entry exists only in the new build.

## Lacked
- **No skill in this repo ever loaded.** All 11 were flat `.claude/skills/*.md`
  files, but Claude Code only discovers `<name>/SKILL.md` with frontmatter.
  Every "run /retro", "/scope", "/release" in CLAUDE.md relied on the agent
  finding the file by hand. Fixed in #991.
- The old `release.md` committed docs onto the release branch, which breaks the
  pure-promotion rule. Following it would have tripped the guard.
- Production sat at v1.4.0 for three months (~25 PRs) and nobody noticed
  until users hit already-fixed bugs (#990).
- An agent can't re-run CI jobs (403), so one random-hint flake in
  `editor-hints.spec.ts` cost a push to make the test deterministic.

## Learned
- A bot-pushed `staging` head leaves `production-promotion-guard` at
  `action_required`. It never runs on the release PR, so verify
  `main..staging == 0` by hand.
- CodeQL's PR gate against production flags the sandbox `new Function` sinks as
  "Code injection" when the diff is large. They're by design, but they block
  the release until dismissed or bypassed.
- Check-run annotations are readable unauthenticated:
  `GET /repos/kemper/partwright/check-runs/<id>/annotations`.

## Longed for
- A lint (or SessionStart check) that fails when `.claude/skills/` contains a
  flat `.md` or a `SKILL.md` without `name`/`description`, so the loader can't
  silently ignore skills again.
- One-time dismissal of the known CodeQL sandbox alerts, or a CodeQL config
  that models the sandbox as intended, so releases don't trip on them.
- The weekly `/release` routine closes #990's staleness gap. Pair it with a
  "production is N weeks behind" alert for when the routine stops.
